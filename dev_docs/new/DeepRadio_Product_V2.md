## 1. DeepRadio 是什么

DeepRadio 在 GNU Radio Companion（GRC）上增加一层自然语言能力：用户用中文或英文描述通信任务，系统生成或修改可运行流图，给出指标、图和可核对的验证结论。

主路径不是让大模型直接写 `.grc`。用户文本进入工作区后，系统识别任务类型、按任务走受控流程、用确定性工具改工程，再把结果折回对话、Claims 和画布。没有配置大模型时，同一套工程事实仍可走确定性路径，产出流图和 Claim-Evidence。

工作区勾选「一句话直出 baseline」才走 LLM 直出 YAML，不经共享工程状态。那是论文对照条件，不是产品主路径。测 Dynamic Workflow 时不要勾选该项。

首版是单会话、单活动任务、串行阶段、仿真优先。硬件配置和受控发射有独立安全边界；未完成真实空口验收前，不得对外说「空口已经通过」。

## 2. 用户能完成的七类任务

任务类型按最终产物、验收方式和安全边界划分，不是按调制方式划分。BPSK、QPSK、QAM、OFDM 是同一类仿真任务里的参数。不要为 BLE 再加第八类任务：空口部署仍属于硬件配置任务中的「部署」操作。

| 用户目标 | 系统任务 | 用户应看到的结果 |
|---|---|---|
| 做一条完整仿真链路并验证 | 端到端仿真 | `.grc`、EVM 等指标、星座/频谱图、当前版本的 Claims |
| 只做发射链路（仿真） | 构建发射机 | 发射机流图和结构校验；不声称已接到真实硬件 |
| 做接收机并测误码 | 构建接收机 | 接收机流图、BER、与发送参考对应的证据 |
| 解释当前工程问题，先别改图 | 诊断 | 原因、证据、最小修改建议；画布和版本不变 |
| 把已有工程改成另一种方案 | 修改工程 | 先停在确认；批准后出新版本并重验；拒绝则工程不变 |
| 只看频谱、星座或指标 | 观测 | 图和指标；工程不被修改 |
| 规划或配置 SDR / 有限发射 | 硬件配置 | 配置、预检、确认；未确认不得发射 |

复合请求按终态范围最大的任务处理。例如「构建 BPSK 并配置到 USRP」走硬件配置，并补齐建图前置。

### 2.1 端到端仿真

规格完整时直接建图并仿真，不应再追问调制方式。EVM 不满足时可自动重试一次；仍失败时必须停下来等用户，不能伪报成功。

代表说法：

```text
做一个 BPSK 过 AWGN 的基带链路，EVM 要小于 10%，并显示星座图和频谱。
```

### 2.2 构建发射机

「只做仿真、不接真实硬件」是约束，不应弹出硬件确认，也不应出现设备发现或发射事件。

代表说法：

```text
构建一个 QPSK 基带发射链路，只做仿真，不接真实硬件。
```

### 2.3 构建接收机

缺少必要接收规格时应先问清楚，用户补充后应延续同一任务，而不是另开一条。BER 必须来自发送参考和接收判决两个数据来源。

代表说法：

```text
构建一个自包含的 BPSK AWGN 接收机，包含定时恢复和判决，并测 BER。
```

### 2.4 诊断

「先不要修改」必须是只读。可以给建议，不能偷偷改图、不能新建快照、不能覆盖 `.grc`。

代表说法：

```text
诊断当前链路的 EVM，解释主要原因并给出最小修改建议，先不要修改工程。
```

### 2.5 修改已有工程

系统先检查当前工程并给出方案，然后停在确认。确认前画布不变。用户点「确认」才改图并重验；点「取消」则工程、版本和画布都不变。

代表说法：

```text
把当前 BPSK 工程改成 QPSK，其余条件不变。
```

### 2.6 观测

不需要修改确认。失败时停下来等用户，不得用旧图冒充本轮产物。

代表说法：

```text
查看当前接收信号的频谱和星座图，给出主峰，只观察不要修改。
```

### 2.7 硬件配置

当前产品可承诺的是：保存流图配置、做预检、展示风险，并在用户确认后写入配置。默认不打开射频，也不把「配置成功」说成「设备已打开 / 已发射 / 手机已收到」。

代表说法：

```text
帮我配置 USRP B210。
```

缺少中心频率和采样率时应等待用户补齐，不能直接完成。用户补齐后延续同一任务，再进入预检和确认。

## 3. 工作区里能看到什么

工作区由三块组成：对话、流图画布、Claims / 测量 / Workflow 详情。

对话区展示用户与 DeepRadio 的自然语言交流。画布展示当前 `.grc`。确认阶段保持当前画布，交付后才刷新。测量区展示 EVM、BER、频谱等指标。Claims 区展示验证状态和 Evidence，且必须对应当前工程版本。

活动条回答「现在处于哪个任务、哪个阶段」：

```text
任务名称 / 任务类型
当前阶段名称
阶段序号 / 阶段总数
执行状态或结果
等待确认原因
确认 / 取消
Claims、指标和规格摘要
```

可折叠的 Workflow Inspector 展示任务下每个阶段的状态、尝试次数、完成计数，以及执行时间线（序号、事件、阶段、执行者）。这是 GTK 面板，不能用浏览器代替验收。

底部状态栏还会显示当前任务、阶段、回复阶段、用户档位、是否等待确认。

当前仍不够完整的展示：逐项失败原因、stale / retry / 失效的可视化历史、阶段执行过程中的逐秒刷新。更细历史以会话文件为准。

## 4. 确认、拒绝、取消、重置

以下操作对用户是产品契约，不是实现细节：

- **确认 / 取消**：只对当前等待点生效。确认后才执行受限修改或硬件相关操作；取消则任务结束且工程不变。
- **改规格**：视为对尚未执行方案的调整，应留在当前任务里。
- **画布保存**：视为工程已变，后续验证结论需要更新。
- **撤销到上一版本**：恢复快照，并同步当前任务版本。
- **重置**：归档当前任务，开始新的会话状态。GUI 重置会触发紧急停止，避免硬件任务残留运行。

未经确认不得执行：调制/配方切换、多块结构修改、硬件配置、真实设备操作、诊断后的大范围修复。

新建纯仿真工程在规格充分时可以直接完成，不必为了「看起来智能」多问一轮。

## 5. 专业度与 CHI

小白、学生、专家是表达和解释档位，不是新的任务类型，也不改变技术验收标准。系统可以用更短或更细的语言，但不能因此放宽「没确认就改图」或「没确认就发射」。

后续实验可量化：任务完成率、首次命中率、确认次数、阶段和工具调用数、失败恢复成功率、总时延、不同专业度用户的轮次与完成质量。研究条件建议至少保留三种：一句话直出 baseline、自由 Prompt 路由、Task Catalog Dynamic Workflow。

## 6. BLE 与 B210：现在能对外说什么

目标示例：

```text
帮我用 B210 发射一个 BLE 信号，local name 为 deepradio，
使手机上的 LightBlue 可以直接扫描到。
```

产品现状：

- 可以离线生成 BLE 广播包、1M 波形和发射流图，并做结构校验。
- 可以只读发现和检查 B210。
- 可以生成 B210 接收实时频谱流图；实时频谱出现在 GNU Radio 的 QT 窗口，不是对话里的 PNG。
- 射频默认关闭。有限时长启动必须同时满足：用户确认射频计划、显式打开功能开关、合法实验环境。
- 当前发射流图只做广告信道 37。要求 37/38/39 轮询的用例还不能登记为通过。
- 真实 B210＋LightBlue 空口尚未人工验收。自动测试通过不等于空口通过。

在完成真实空口验收前，不要说：

```text
设备已经打开
Flowgraph 已启动
RF 已发射
手机已收到信号
LightBlue 已扫描到 deepradio
OTA 已经通过
```

空口成功只能由人工观察（LightBlue 截图）或独立接收设备证明，不能由发射端自证。

## 7. 首版交付边界

首版包含：单会话单任务、串行阶段、用户确认与取消、仿真构建/观测/诊断/修改、硬件配置与预检展示、离线 BLE 工件。

首版不包含：多任务排队、并行阶段、跨工程任务、把「配置成功」当成真实部署成功、未确认的射频发射。
