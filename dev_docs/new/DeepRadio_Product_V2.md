## 0. 2026-08-29 增量：真实输入下的意图对齐与用户控制

### 0.1 产品问题分析

当前七类 Task 的代表句过于完整、彼此正交，不能代表实际用户。真实用户更可能只说“我要用硬件发射一段 BLE 信号”，此时系统既不知道具体设备和广播名称，也不能把协议默认值、用户事实和安全默认值混为一谈。旧链路还存在三个用户体验缺口：缺参问题主要依赖聊天文本；Workflow 建立后才暴露歧义；执行中修改要求时，用户看不到哪些步骤和产物会失效。

诊断体验也不完整。软件流图、驱动、设备发现、型号一致性、运行日志、物理接线和空口结果属于不同证据层。系统不能因为 `iio_info` 成功就声称天线或线缆正确，也不能因为流图生成成功就声称硬件已经运行。

### 0.2 产品方案

统一体验改为：

```text
描述目标
→ 识别意图草案
→ 用选择题/自定义输入补齐关键参数
→ 用户确认 SharedIntent
→ 建立可观察 Workflow
→ 自动执行安全步骤
→ 在工程写入或 RF 操作前再次确认
→ 观察证据并允许随时修改
```

产品必须区分两种确认：

- **意图确认**：确认“要做什么、使用什么参数、成功标准是什么”，确认后才建立 Workflow；它不授予硬件或 RF 权限。
- **操作确认**：确认具体副作用，例如改图、设备配置或有限时长 RF 发射；只有 `rf_authorization` 可以授予 `RF_RUN`。

状态栏新增用户可见的 `SharedIntent id / revision / status / hash`。缺参时显示选择项和自定义输入；确认前状态为 `awaiting_input/awaiting_confirmation`。执行中修改语义参数时，系统先停止活动 RF（如有），展示新 revision 和影响范围，再由用户确认后重新编织受影响流程。语言风格档位只改变解释方式，不改变意图、参数、工具和安全边界。

七类 Task 继续作为评测覆盖标签，而不是产品菜单或输入模板。产品能力由目标、能力、参数、证据和副作用组合决定，新协议或新硬件不应要求用户套用某个 Task 句式。

## 1. 产品定位

DeepRadio 是 GNU Radio Companion 内的自然语言通信工作区。用户用中文或英文描述目标，系统理解任务、生成或修改流图、执行仿真或受控硬件操作，并将当前 Workflow、工程状态、测量、证据和下一决策点展示在同一界面。

产品不是“一句话生成脚本”的包装器。它的核心体验是：

```text
用户表达目标
→ 系统展示可观察的动态 Workflow
→ 自动完成安全且确定的步骤
→ 在修改工程或发射前让用户控制
→ 根据用户决定和执行反馈更新后续步骤
→ 用产物与 Evidence 支撑结论
```

七类 Task 是当前测试和产品说明中的代表目标，不是对用户表达方式的限制。用户可以提出复合目标，系统应按能力和决策边界组织流程，而不是把输入强行改写成某一条测试句式。

## 2. 当前已观察到的能力

0827 V3 人工实验中，以下七类主路径均完成：

| 用户目标 | 用户应获得的结果 |
|---|---|
| 端到端仿真 | 可运行 `.grc`、指标、需要的星座/频谱和结论 |
| 构建发射机 | 发射链路、结构校验；声明只仿真时不接触硬件 |
| 构建接收机 | 接收链路、必要参数补充、BER 等质量证据 |
| 诊断当前工程 | 原因、证据和最小建议；只读要求下工程不变 |
| 修改当前工程 | 修改计划、用户确认、修改后工程和重新验证 |
| 观察当前工程或信号 | 指定图与指标；不修改工程 |
| 配置 SDR | 安全预览、设备探测和明确停止点；未授权不发射 |

0828 V2 人工实验中，PlutoSDR 在 2.402 GHz 发射 BLE 广播，手机 LightBlue 扫描到 `Deepradio27`，受控进程随后停止。这证明了该次实验的端到端可达性，不等于最新代码的全部能力已完成回归。

## 3. 需要统一的用户可见语义

### 3.1 “完成”不是单一绿色状态

界面应同时展示三个维度：

```text
任务结果：passed / failed / cancelled
运行质量：clean / warning / failed
证据等级：system_verified / human_statement / attached_capture / independent_receiver
```

例如，手机成功收到 BLE 但发射日志出现 underflow，应显示“目标完成，运行质量有警告”，不能显示成无条件的完全成功。

### 3.2 离线观察与实时观察必须区分

- “查看当前工程的频谱”可以运行当前离线流图并分析其数据。
- “查看 Pluto/B210 当前接收信号”必须走真实设备接收链。
- 文本无法判断来源时，系统应询问用户，而不是静默选择离线仿真并称为实时。

界面规格摘要必须显示数据来源，例如：

```text
QPSK 基带 TX → File Sink
BPSK/AWGN 离线工程 → 频谱与星座
PlutoSDR 实时 RX → QT Frequency Sink
BLE 1M / Ch37 → PlutoSDR TX
```

不得再显示无意义的 `?`。

### 3.3 修改与重建必须区分

用户说“把当前 BPSK 改成 QPSK”时，默认含义是保留当前工程并做最小修改。系统应展示修改 diff，并说明哪些块和参数保持不变。只有用户明确要求重建，或当前图无法安全局部修改时，才使用 recipe 重建，并在确认前说明影响范围。

### 3.4 三种确认不能混用

| 确认目的 | 产品文案 | 授权效果 |
|---|---|---|
| 配置交付 | 确认已保存 / 继续发射 | 不授予 RF 发射 |
| RF 授权 | 确认有限时长发射 | 授予本次绑定计划的 `RF_RUN` |
| 空口观察 | 已在接收端看到 / 未看到 | 只记录 Evidence，不授予设备操作 |

“停在发射确认”应交付安全预览并停止；不能因为用户点击“确认已保存”就把 RF plan 写成已获发射授权。

### 3.5 回复只陈述已发生的事实

- 只有 ArtifactIndex 中真实存在的图片、报告和流图才能出现在回复中。
- BER=0 必须附带样本量和统计限定。
- “主峰”必须说明是否排除 DC、频率分辨率和测量来源。
- “设备已打开”“正在发射”“手机已收到”必须分别由 runtime 和外部 Evidence 证明。

## 4. Workflow 可观测性与人的控制

Inspector 默认显示：

- 用户原始目标和系统提取的 Intent；
- 当前 Task 评测标签、当前 Stage、已完成/等待/未执行步骤；
- 本 Stage 使用的是规则、LLM 还是确定性 handler；
- 当前工程版本、产物、Measurement 和 Claims；
- 下一决策点的目的、影响范围和授权等级；
- runtime 的 `run_id`、剩余时长、是否活跃、停止原因和质量告警。

人的正向控制：确认、拒绝、改规格、取消、重试和紧急停止。

人的逆向控制：用户在 GRC 画布手工修改并保存后，系统检测工程 hash/version 变化，只失效受影响的 Measurement 与 Claims，并重新规划必要的后续 Stage；不得回滚或忽略用户修改。

这构成论文中可强调的 dynamic state：下一步不是固定脚本，而由“当前事实 + 用户决定 + 反馈影响范围”共同决定，同时安全副作用仍由确定性 Policy 约束。

## 5. PlutoSDR BLE 产品流程

```text
用户输入协议、名称、设备、频率和最长时长
→ 生成 BLE PDU/波形与禁用 RF 的预览流图
→ 离线协议校验
→ 发现并探测用户指定设备
→ 展示绑定设备与参数的 RF 计划
→ 用户明确授权
→ arm 并有限时长发射
→ 用户或独立接收端提交空口观察
→ 自动/人工停止并显示运行质量
```

当前 BLE 发射能力按单个广告信道声明。2.402 GHz 对应广告信道 37。三信道跳频、独立 BLE sniffer 自动验收不在当前产品承诺内。

LightBlue 的“已看到”按钮可以记录人工观察，但只有截图被复制到 session、生成 hash 并绑定 `run_id` 后，才能称为带附件的实验 Evidence。

## 6. 当前产品缺口与完成条件

当前缺口：版本指纹不可见、LLM 调用不可审计、部分回复与产物不一致、修改任务可能重建工程、离线/实时观察混淆、配置确认与发射授权语义接近、underflow 和 Evidence 不完整不够醒目。

产品完成条件：

1. 七类代表任务在同一最新版本上重新通过；
2. Pluto BLE 在同一版本上再次被独立接收端看到；
3. Inspector 能解释每轮 Intent 和执行模式；
4. 任一“完成”结论都能追溯到状态、产物和证据；
5. 用户能在所有工程写入和 RF 副作用前控制流程，也能通过手工修改画布触发局部重规划。
